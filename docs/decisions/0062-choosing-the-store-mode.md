# ADR 0062: Choosing the store mode

Date: 2026-11-26. Status: accepted under the owner's migration charter, step 1, slice 6. Builds on [ADR 0045](0045-per-project-store-mode.md) and [ADR 0061](0061-repository-store-mode.md).

## Decision

1. **Showing and choosing the mode is a product action.** `GET /api/v1/projects/{id}/store-mode` shows the recorded mode. It also shows whether the store resolves now, and if not, the same 409 text a component request would get. It lists the modes the project can switch to: runtime, and repository for each registered repository. `PUT` with `{"mode":"runtime"}` or `{"mode":"repository","repository":"<id>"}` writes `store.json`. The actions are cataloged as `projects.storemode.show` and `projects.storemode.set`, with client methods `storeMode` and `setStoreMode`. The desktop control is "Where component data lives" in Project components. The terminal commands are `store-mode` and `set-store-mode --mode … [--repository …]`.
2. **Only working modes can be chosen.** Both mode answers 409 until it is usable. A repository must be registered for the project, or the request answers 422. Its checkout must pass the checks of ADR 0061, or the request answers 409. A repository whose stores are not initialised yet can still be chosen. Component requests are then refused until the developer initialises those stores, as ADR 0061 decision 3 says.
3. **Records are never moved or merged.** A change is refused with 409 in three cases. The first is when the project keeps Luuna-tracked records in its current store: a ticket handed to Missions, or a live memory binding. Switching would leave them behind, unreachable. The second is when a component write for the project reached its component without recording an outcome (a runtime stopped mid-write): it may have landed in the current store, so it must be retried with its idempotency key and reconciled first. The third is when any component store on the chosen side already holds records. A store counts as empty when it is absent, or when every file other than its top-level `config.yaml`, `README.md`, `.gitignore` and `.gitattributes` is blank. A link, a FIFO or other special file (never opened), an unreadable entry or a store too large to scan (10,000 entries, 8 levels or 16 MiB read) counts as holding records. Roots initialisation resolves its store under the same component lock, so it never writes to a store a change has just left. A hand-written `store.json` is still the developer's own explicit choice, as ADR 0045 allows.
4. **The write is serialised and hardened.** The change holds the component lock, so no component operation runs against the old store while the file changes. Two writers never race on the temporary file. Choosing the current mode again writes nothing. A change records a `project.store_mode.changed` project event with the old and new mode. Slice-1 follow-ups 2, 3, 4 and 6 are closed:
   - The read opens `store.json` without following a link and without blocking on a FIFO (`O_NOFOLLOW | O_NONBLOCK` on Unix, `FILE_FLAG_OPEN_REPARSE_POINT` on Windows), and the opened handle must be a regular file.
   - The write creates `projects/` and `projects/<id>/` one folder at a time, re-checks each one after it is created, and makes existing folders 0700 on Unix.
   - `luuna-storage` gains a direct `libc` dependency on Unix only. It is already in the lockfile through other workspace crates.

## Consequences

A developer can move a fresh project into a repository's own stores, or back, from either client. Moving a project that already has tickets or memory still means starting a new project, or emptying and re-creating its records, because Luuna does not migrate records between stores.

## Evidence

The runtime tests in `crates/luuna-runtime/tests/store_repository_git.rs` use real temporary git checkouts. They cover showing the mode and its choices, choosing a repository, checking that component requests then reach it, choosing it again with no write and no event, and switching back. They also cover the refusals: both mode, an unregistered repository, a malformed body, a target store that already holds a record, and a project with memory in its current store. In each refused case `store.json` stays unchanged. A unit test covers what counts as a record. The terminal formatter and the catalog contract checks cover the new actions.
