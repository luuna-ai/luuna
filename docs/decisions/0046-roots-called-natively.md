# ADR 0046: Roots called natively

Date: 2026-11-12. Status: accepted under the owner's signed migration charter (step 2).

Builds on [ADR 0044](0044-one-repository-and-agent-shipping.md) and [ADR 0045](0045-per-project-store-mode.md), which remain in force. It supersedes no ADR.

## Context

Luuna Roots was imported into `roots/` with its history. It was a separate Cargo workspace, and the runtime did not call it. The migration moves the maintained components into this repository and calls them natively, one at a time. Roots is first.

Calling roots-core from the runtime raises four questions. How does a crate in `roots/` join the build without moving files or changing a locked dependency? Roots needs `serde_json` with `preserve_order`, and two stored hashes in the runtime were computed over JSON text whose key order came from the default sorted map. roots-core takes the acting identity as a plain string and does not check it when a proposal is accepted or rejected, so the runtime has to say what a human and an agent are. And where does Roots data live, and who creates it?

## Decision

1. **roots-core joins the root workspace in place.** `roots/crates/roots-core` stays where it is and is listed in the root `Cargo.toml` as `members = ["crates/*", "roots/crates/roots-core"]`. It is removed from the members list of `roots/Cargo.toml`. roots-cli stays in the `roots/` workspace and keeps its path dependency on `../roots-core`. `roots/Cargo.lock` is unchanged and keeps locking roots-cli's build. `luuna-runtime` depends on roots-core by path. Folding roots-cli in too was rejected: it would delete `roots/Cargo.lock`, and the two lock files pin different versions of `libc`, so Roots would build against a lower locked version. Moving the crates under `crates/` was rejected: it breaks fixture paths in roots-cli's tests and the crate enumeration in the smoke script.
2. **roots-core's manifest is literal.** It no longer inherits from a workspace. It writes `version = "0.0.0"`, `edition = "2024"`, `rust-version = "1.85"` and `license = "MIT"`, and its seven dependencies exactly as the Roots workspace wrote them. The version stays `0.0.0` because `roots_core::VERSION` is the package version and the Roots command prints it. It sets no `authors` or `repository` key; no code reads them, and attribution stays in `roots/LICENSE`, `roots/UPSTREAM.md` and `THIRD-PARTY-NOTICES.md`.
3. **The path dependency stays inside the workspace rule.** [ADR 0044](0044-one-repository-and-agent-shipping.md) and the charter forbid dependencies on anything outside the workspace. roots-cli's dependency on roots-core and the runtime's dependency on roots-core both point at a crate that is in this repository and in the root workspace.
4. **Toolchains and checks.** `roots/rust-toolchain.toml` (1.99.1) is unchanged. Commands run from the repository root use Luuna's pin (1.90.0), and the Roots checks keep `RUSTUP_TOOLCHAIN=1.90.0`. The five Roots checks stay as they were. Nothing under `roots/` changes except the two manifests above.
5. **`preserve_order` is on for the workspace, and the two stored hashes no longer depend on it.** roots-core requests `serde_json` with `preserve_order`, and Roots needs it. With the feature on, JSON objects keep insertion order instead of sorted order. Two stored values were SHA-256 over compact JSON text and would have changed: the executor environment fingerprint (compared against stored baseline evidence) and the Missions ticket source hash (stored as the ticket source revision). Both now sort keys explicitly (a `BTreeMap` in the executor; a recursively key-sorted compact form in Missions), which produces the same bytes the sorted map produced. Pinning tests added before the change hold the digests taken from the previous code, and neither test file changes after it. `luuna-domain` is not edited.
6. **Cosmetic key-order changes are accepted.** With the feature on, the key order of JSON text in newly written SQLite rows built from `json!` values, of runtime HTTP JSON responses, of `luuna-tui --print-config`, of Beacon runtime payloads and of Pi session-event summaries follows insertion order. Existing rows keep their text. Nothing hashes or byte-compares these texts, clients read by key, and no schema or golden file pins the order. A fresh search of the workspace, `roots/` included, for hashes, signatures and byte comparisons over serialised `serde_json` text is recorded in the plan's hand-off.
7. **Human and agent identity are built by the runtime.** The trust anchor for a human is the runtime's bearer-authenticated local API. The token is held by the clients the user drives and is never in an agent process's environment. A human-only operation takes a `HumanActor`, which has a private field and one constructor, `HumanActor::local_user(name)`. The constructor accepts a plain name or `human:<name>`, refuses anything roots-core does not classify as a human, and may be called only from a handler behind the authenticated router. An agent operation takes an `AgentActor`, whose only constructor, `AgentActor::for_run`, loads the run from the runtime's own store, refuses an unknown run or a run of another project, and forms `agent:run-<run id>`. No identity is read from environment variables, git configuration or `.luuna` files.
8. **No roots-core function that starts a process or reads the environment is exposed.** The module does not call the actor resolvers that read git configuration or the environment, the drift and verify functions, the workspace and project-root discovery functions, or the path functions that search upward. Reads, proposals, questions, sprouts, accept and reject start no process. Static checks over the runtime sources keep it so.
9. **The Roots store is in the project store and is never created here.** `RootsStore::for_project` takes the project store from `stores.rs` (the resolver of [ADR 0045](0045-per-project-store-mode.md)) as an absolute path and puts Roots data at `<store>/.luuna/roots`, beside the Missions, Atlas and Beacon data. Repository and both modes are refused by the resolver as today. There is no upward search, and no checkout's `.luuna` folder is read. A project without `.luuna/roots/config.yaml` in its store answers 409 "Roots is not set up for this project". Enabling a project does not initialise a Roots store, and this module does not either: Roots' own initialisation lives in roots-cli, and writing it again here could drift from Roots' stored format.
10. **The Roots license notice ships with the binary.** The runtime binary now contains Roots code, so `THIRD-PARTY-NOTICES.md` states this and carries the text of `roots/LICENSE`. That file is already copied into the Windows package.
11. **Every operation is async.** The module resolves the store, then runs roots-core on the blocking pool, because roots-core takes file locks that sleep while they wait. Roots errors map to 404, 409, 403, 422 or 500, and messages carry no host path.

## Consequences

- The root `cargo fmt`, `cargo clippy` and `cargo test` commands now build, lint and test roots-core. roots-cli, its fixtures and its lock file are unchanged, and the Roots workspace commands still work.
- `Cargo.lock` gains roots-core and the packages it needs. No existing locked dependency is removed or re-versioned.
- Baseline fingerprints and Missions source revisions stored before this change still match.
- `crates/luuna-runtime/src/roots.rs` is a public module with no caller in a route yet. The later plan, s2-roots-intent, adds the pieces this decision leaves out: HTTP routes, capability catalog entries with their client methods, TUI commands and `luuna intent`, Roots store initialisation, the source of the human name passed to `HumanActor::local_user` (which must keep human routes unreachable from agent sessions), and any exposure of drift or verify, which must pass an environment built by the component adapter's rules (cleared, allow-listed, private home, no `ROOTS_*` names).
- Missions, Atlas and Beacon are unchanged: they remain pinned submodules until their ports land.
